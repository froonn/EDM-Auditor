# План разработки: `feature/database-schema`

## 1. Назначение этапа

Создать устойчивый слой хранения для `EDM-Auditor` на базе SQLite. Слой должен
сохранять документы, результат работы парсера и сущности, которые понадобятся
для базы нормативно-правовых актов и последующего аудита.

Результатом этапа является версионируемая схема базы данных, набор моделей и
репозиториев для доступа к данным, а также тесты, подтверждающие целостность
связей и сохранение результата `ParsedDocument`.

## 2. Цели и результат

После завершения этапа система должна:

1. Создавать SQLite-базу с управляемой версией схемы.
2. Хранить пользователей и их роли без реализации аутентификации.
3. Хранить метаданные документов, исходный текст и статус обработки.
4. Хранить абзацы документа вместе с индексом, диапазоном символов и номером
   страницы, полученными от `document_parser`.
5. Хранить нормативно-правовые акты и правила аудита с их связями.
6. Хранить отчёты аудита и отдельные найденные нарушения.
7. Обеспечивать внешние ключи, уникальные ограничения и базовые индексы.
8. Позволять очищать тестовую базу и повторно применять схему без ручного
   редактирования SQLite-файла.

## 3. Границы этапа

### Входит в этап

- SQLite-конфигурация и создание подключения;
- ORM-модели или эквивалентные типизированные модели хранения;
- миграция начальной схемы;
- таблицы пользователей, документов и абзацев;
- таблицы НПА, правил, отчётов и нарушений;
- перечисления или валидаторы для статусов, ролей, серьёзности и типов
  проверок;
- репозитории для документов и связанных абзацев;
- преобразование `ParsedDocument` в записи базы данных;
- unit- и integration-тесты схемы и репозиториев;
- документация запуска миграций и тестов.

### Не входит в этап

- регистрация, вход и авторизация пользователей;
- HTTP endpoints и загрузка файлов через FastAPI;
- вызов парсера из API;
- OCR, NER, RAG, LLM и выполнение правил аудита;
- наполнение базы реальными нормативными актами;
- интерфейс frontend;
- сложные миграции существующих production-данных.

## 4. Предлагаемая структура модулей

```text
backend/

  src/
    edm_auditor/
      database/
```

Название ORM и инструмента миграций должно быть выбрано в начале реализации
и зафиксировано в `pyproject.toml`. Предпочтительный вариант — SQLAlchemy 2.x
для моделей и Alembic для миграций, без привязки остального к ORM API.

## 5. Модель данных

### 5.1. Пользователи

Таблица `users`:

- `id` — первичный ключ;
- `username` и `email` — обязательные уникальные значения;
- `hashed_password` — обязательное значение, не используемое для проверки
  пароля на этом этапе;
- `role` — `admin`, `auditor` или `hr`;
- `created_at` — время создания записи.

### 5.2. Документы и абзацы

Таблица `documents`:

- `id` — первичный ключ;
- `user_id` — необязательная ссылка на владельца;
- `title`, `file_type`, `file_path` — обязательные метаданные;
- `raw_text` — нормализованный текст из `ParsedDocument`;
- `classified_type` — тип документа, заполняемый позднее;
- `status` — `uploaded`, `processing`, `audited` или `error`;
- `created_at`.

Таблица `document_paragraphs` должна дополнить схему из ТЗ:

- `id` — первичный ключ;
- `document_id` — обязательная ссылка на документ с каскадным удалением;
- `paragraph_index` — индекс абзаца в исходном порядке;
- `text` — текст абзаца;
- `start_char` и `end_char` — диапазон в `documents.raw_text`;
- `page_number` — номер страницы PDF или `NULL` для DOCX.

Для пары `document_id` и `paragraph_index` нужен уникальный индекс. Диапазон
должен сохранять контракт парсера: `raw_text[start_char:end_char] == text`.

### 5.3. НПА и правила

Таблица `legal_acts` хранит код, название, номер и содержание статьи, а также
необязательную ссылку на источник.

Таблица `audit_rules` хранит уникальный `rule_code`, название, тип документа,
серьёзность, описание, тип проверки, JSON-параметры, активность и ссылку на
`legal_acts`.

На этом этапе записи могут создаваться через репозиторий или seed-скрипт, но
готовый набор статей законодательства в репозиторий не добавляется.

### 5.4. Отчёты и нарушения

Таблица `audit_reports` связана с `documents` и содержит агрегированные
счётчики нарушений и итоговое описание.

Таблица `audit_findings` связана с отчётом и необязательно с правилом. Она
хранит серьёзность, описание, диапазон символов, цитату, ссылку на статью и
рекомендацию. Диапазоны должны ссылаться на текст документа, но проверка
юридического смысла диапазона остаётся задачей `audit-engine`.

## 7. Требования к целостности и ошибкам

- Ошибка подключения или миграции должна быть явно возвращена вызывающему коду
  и не маскироваться пустым результатом.
- Запись документа и его абзацев должна выполняться в одной транзакции.
- Нельзя сохранять абзац без существующего документа.
- Нельзя молча перезаписывать документ при конфликте идентификатора.
- Удаление документа не должно оставлять осиротевшие абзацы, отчёты или
  нарушения.
- JSON-параметры правил должны быть валидным JSON либо `NULL`.
- Внешние ключи SQLite должны быть включены для каждого подключения.

## 8. Критерии готовности

Этап считается завершённым, если:

- чистая SQLite-база создаётся одной документированной командой;
- миграция применяется без ручного изменения SQL-файлов;
- все таблицы из ТЗ и `document_paragraphs` присутствуют;
- связи и ограничения проверены автоматическими тестами;
- результат текущего `document_parser` сохраняется и загружается без потери
  текста, порядка, диапазонов и номеров страниц;
- сбой транзакции не оставляет частично сохранённые данные;
- тесты базы данных проходят независимо от содержимого рабочей базы;
- документация объясняет настройку и проверку базы.

## 9. Команда проверки

Из каталога `backend/`:

```bash
pytest tests/database -q
```

Для проверки миграций дополнительно:

```bash
alembic upgrade head
alembic downgrade base
```

Конкретные команды должны быть скорректированы после выбора инструмента
миграций и добавлены в `backend/README.md`.

## 10. Рекомендуемая последовательность коммитов

```text
build(db): add database dependencies
feat(db): define storage models
feat(db): add initial migration
feat(db): persist parsed documents
test(db): cover schema and repository constraints
docs(db): document database setup
```

Все изменения этапа выполняются в ветке `feature/database-schema`. После
завершения ветка должна быть готова к merge в `master`, не требуя frontend,
FastAPI или RAG-компонентов.
