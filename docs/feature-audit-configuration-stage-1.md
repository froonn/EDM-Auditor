# План разработки: `feature/audit-configuration-stage-1`

> **Статус:** планируется. Первый этап текущей ветки `feature/audit-configuration`.
> Этап посвящён надёжной загрузке НПА, извлечению правил по частям, сохранению
> provenance и диагностике неполного результата. Изменение поведения аудита
> пользовательских документов допускается только там, где оно необходимо для
> корректной работы с новыми правилами.

## 1. Назначение этапа

Устранить риски, возникающие при генерации правил из нормативно-правового акта:

- передача слишком большого НПА одним запросом в LLM;
- потеря правил из-за ограничения context window или `max_tokens`;
- отсутствие информации о том, из какой статьи и цитаты создано правило;
- генерация русскоязычных правил на английском языке;
- принятие невалидных или неприменимых параметров;
- тихое отбрасывание части правил;
- успешный статус загрузки при частично обработанном НПА;
- потеря правил из-за глобальных коллизий `rule_code`;
- запись полных prompt и ответов модели в логи.

Результатом этапа должен стать воспроизводимый pipeline:

```text
upload
  -> parse and normalize
  -> detect logical sections
  -> split into source-preserving chunks
  -> extract rules per chunk
  -> validate, localize and normalize
  -> deduplicate
  -> persist rules with provenance
  -> publish processing status and diagnostics
  -> rebuild RAG index
```

## 2. Цели и результат

После завершения этапа система должна:

1. Обрабатывать НПА несколькими LLM-вызовами по логическим фрагментам, а не
   передавать весь текст одним запросом.
2. Сохранять диапазон и точную цитату исходного НПА для каждого сгенерированного
   или отклонённого правила.
3. Требовать, чтобы название, описание, цитата и текстовые параметры правила
   сохраняли язык источника.
4. Проверять, что параметры правила соответствуют `check_type` и текущему
   контракту валидаторов.
5. Различать полностью обработанный, частично обработанный и неудачный НПА.
6. Показывать количество обработанных chunks, полученных, принятых и
   отклонённых правил.
7. Не терять базовые диагностические данные при сбое одного chunk-а или
   одного ответа модели.
8. Делать коды правил уникальными в пределах НПА и стабильными при повторной
   обработке неизменного текста.
9. Не записывать в логи полный текст НПА, prompt или raw response модели.
10. Сделать онлайн-провайдер обязательным для production-обработки НПА, а
    offline-провайдер оставить только для тестов, CI и локальной разработки без
    сети.

## 3. Границы этапа

### Входит в этап

- модель состояния обработки НПА и диагностик;
- логическое разбиение TXT-текста на статьи, пункты, абзацы и chunks;
- source-preserving диапазоны и стабильные идентификаторы chunks;
- batch или последовательный вызов `RuleExtractionProvider` для chunks;
- локализация prompt и результата на язык исходного НПА;
- валидация схемы правила и параметров конкретного validator-а;
- проверка цитаты, диапазона, языка и применимости правила;
- дедупликация правил и стабильная генерация `rule_code`;
- сохранение provenance и результатов обработки;
- безопасное поведение при ошибках LLM, fallback и partial result;
- API-ответ и web UI с диагностикой загрузки;
- unit-, integration- и regression-тесты на синтетических русскоязычных НПА;
- обновление документации запуска и ограничений.

### Не входит в этап

- OCR и поддержка новых форматов НПА;
- обучение собственной модели или fine-tuning;
- автоматическое юридическое утверждение правил;
- авторизация, RBAC и разграничение доступа;
- полноценный асинхронный distributed worker;
- выбор production embedding-модели и расширение корпуса НПА;
- генерация исправлений для пользовательских документов;
- изменение severity или юридического смысла правила только на основании
  вывода LLM;
- автоматическое включение сомнительных правил без прохождения validator-а.
- поддержка production-аудита без доступного онлайн-провайдера;
- сохранение `EDM_NEURAL_MODE` как обязательной пользовательской настройки.

Если обработка в текущем API останется синхронной, должен быть предусмотрен
совместимый контракт для будущего фонового запуска: загрузка и получение
статуса не должны зависеть от конкретного способа выполнения.

### 3.1. Политика провайдера

В рабочем production-сценарии генерация правил из НПА выполняется только через
настроенный онлайн-провайдер. Недоступность провайдера, отсутствие ключа,
таймаут или невалидный ответ не должны приводить к статусу `completed` и не
должны выдавать пользователю ложный успешный результат.

Переменная `EDM_NEURAL_MODE` не нужна как часть production-контракта и должна
быть удалена из пользовательской конфигурации. Политика `required` фиксируется
в application service: если онлайн-извлечение обязательно, ошибка обработки
возвращается явно, а НПА получает `failed` или `partial` согласно фактически
опубликованным результатам.

Offline-провайдер не является альтернативным production-режимом. Он сохраняется
для unit/integration-тестов, CI и локальной разработки без сети и API-ключей.
Выбор конкретного онлайн-провайдера и модели по-прежнему выполняется через
`EDM_MODEL_PRESET`; например, `google-ai-studio` или `lm-studio`.

## 4. Текущие проблемы и целевые инварианты

### 4.1. Размер входа

Текущий провайдер добавляет весь `parsed.text` в один prompt. В новой версии
размер каждого запроса должен ограничиваться конфигурацией:

- максимальный размер chunk в символах или токенах;
- максимальный размер prompt;
- максимальный размер ответа;
- максимальное число правил в одном ответе.

Превышение лимита должно приводить к разбиению chunk-а или явной ошибке, а не к
молчаливому усечению текста.

### 4.2. Покрытие текста

Для каждого НПА должны быть известны:

```text
chunks_total
chunks_processed
chunks_failed
rules_returned
rules_accepted
rules_rejected
rules_deduplicated
```

Нельзя считать обработку успешной, если chunk не был обработан и это не
отражено в диагностике.

### 4.3. Язык

Язык источника определяется до вызова LLM и сохраняется в результате
обработки. Для первой версии минимально поддерживается русский язык (`ru`).
Если язык не определён или не поддерживается, загрузка должна получить явный
статус `failed`/`partial`, а не создавать правила с неизвестным языком.

Для русскоязычного НПА:

- `name` и `description` должны быть на русском;
- `keywords`, `query` и текстовые значения параметров должны браться из
  исходного текста или сохранять его терминологию;
- `source_quote` должна быть точной цитатой НПА;
- `rule_code`, `check_type`, `severity` и другие enum могут оставаться
  техническими англоязычными значениями;
- латинские аббревиатуры, номера и обозначения не должны ошибочно считаться
  нарушением языка.

Проверка языка является защитой от очевидного смешения языков и предупреждением
для ручной проверки, а не заменой юридической экспертизы или полноценного
лингвистического классификатора.

**Метод определения языка:** для первого прохода достаточна быстрая эвристика
без внешних зависимостей — доля символов кириллицы в тексте НПА (например,
`cyrillic_ratio > 0.4` → `ru`). Добавление тяжёлых библиотек (`langdetect`,
`lingua`) в `pyproject.toml` не предусмотрено в рамках этого этапа.
*Примечание:* Эвристика должна корректно обрабатывать наличие латинских аббревиатур, формул и смешанного текста, а также предоставлять возможность явного ручного/параметрического переопределения языка (`source_language`) при загрузке.

### 4.4. Модель выполнения и лимиты провайдеров

Последовательная обработка 10–20 чанков означает 10–20 HTTP-вызовов к LLM.
Это порождает два риска:

**Таймауты клиента.** При 15–20 чанках суммарное время выполнения может
достигать 30–90 секунд в зависимости от провайдера, что приведет к тайм-ауту стандартных HTTP-клиентов и прокси при синхронном запросе. Для решения этой проблемы рекомендуется использовать фоновые задачи (`FastAPI BackgroundTasks` или асинхронный воркер), возвращающие ответ немедленно (`202 Accepted` или `200 OK` со статусом `processing_status: processing`), после чего клиент опрашивает статус через эндпоинт диагностик.

**Rate limits провайдеров.** У разных провайдеров принципиально разные
характеристики:

| Провайдер             | Типичный лимит    | Рекомендуемая пауза между чанками |
|-----------------------|-------------------|-----------------------------------|
| Google AI Studio Free | 15 RPM            | 4 сек                             |
| OpenRouter (платный)  | зависит от тарифа | 0.5–1 сек                         |
| LM Studio (локально)  | нет лимита RPM    | 0 (но большой `timeout_seconds`)  |
| Stub (тесты / CI)     | нет ограничений   | 0                                 |

Обработка каждого чанка должна быть последовательной с настраиваемой паузой
`inter_chunk_delay_seconds` и ограниченным числом retry с экспоненциальным
backoff при получении HTTP 429 / `ResourceExhausted`. Бесконечные повторы
запрещены; превышение `retry_attempts` должно давать статус `failed` для чанка.

Все эти параметры (пауза, таймаут, число retry) хранятся в профиле экстрактора
в `config/models.toml`, а не в `.env`:

```toml
[profiles.extractor.google-ai-studio]
provider = "google-ai-studio"
model = "gemini-3.1-flash-lite"
api_key_env = "GEMINI_API_KEY"
temperature = 0.2
max_tokens = 2000
structured_output = "json_schema"
request_timeout_seconds = 30.0
retry_attempts = 3
retry_backoff_factor = 2.0
inter_chunk_delay_seconds = 4.0   # 15 RPM ≈ 1 запрос / 4 сек

[profiles.extractor.stub]
provider = "stub"
model = "stub-v1"
request_timeout_seconds = 5.0
retry_attempts = 0
inter_chunk_delay_seconds = 0.0
```

```text

    test_deduplication.py
```

Допускается разместить часть логики в существующих `api` и
`model_providers.py`, если доменные контракты останутся отделены от FastAPI и
конкретного LLM-провайдера. Провайдер должен получать один подготовленный
chunk и возвращать структурированный результат; он не должен знать о
SQLAlchemy, HTTP endpoint или жизненном цикле `LegalAct`.

## 6. Контракты и модель данных

### 6.1. Source chunk

Каждый chunk должен содержать:

- стабильный `chunk_id`;
- `legal_act_id` или временный идентификатор до сохранения НПА;
- `section_id`, тип секции и номер статьи/пункта, если они обнаружены;
- `start_char` и `end_char` в нормализованном исходном тексте;
- точный `text`;
- `chunk_index`;
- версию алгоритма chunking;
- язык источника.

Обязательный инвариант:

```python
legal_act.article_text[start_char:end_char] == chunk.text
```

Если нормализация меняет длину текста, необходимо хранить отображение
координат либо выполнять chunking после сохранения именно той версии текста,
которая используется при проверке цитаты. *Важно:* Нормализация переносов строк (`\r\n` в `\n`), удаление BOM и лишних пробелов должны производиться **строго один раз** до сохранения в БД и построения чанков, чтобы предотвратить расхождение смещений (offsets).

### 6.2. Extracted rule

Внутренний результат LLM должен содержать:

- локальный идентификатор правила в chunk-е;
- `name`, `description`, `severity`, `check_type`;
- `parameters`;
- `source_quote`;
- необязательный диапазон внутри chunk-а;
- `source_article`/`source_section`;
- язык результата;
- диагностические признаки, если правило требует ручной проверки.

LLM не должна возвращать произвольные поля, которые меняют domain-контракт.
Неизвестные поля могут быть проигнорированы только после явного логирования
счётчика, но неизвестные обязательные значения должны отклоняться.

### 6.3. Контракт параметров по `check_type`

Валидация должна проверять не только наличие поля `parameters`, но и точное
соответствие его ключей контракту конкретного валидатора:

| `check_type` | Обязательные ключи                             | Допустимые типы / значения                                                              |
|--------------|------------------------------------------------|-----------------------------------------------------------------------------------------|
| `keyword`    | `keywords` — непустой список строк             | `mode`: `"forbidden"` (по умолч.) / `"required"`; `match_mode`: `"word"` / `"contains"` |
| `regex`      | `pattern` — строка, компилируемая `re.compile` | —                                                                                       |
| `numeric`    | хотя бы одно из `min`, `max`                   | `entity`: `"money"` / `"number"` / `"percentage"`                                       |
| `date`       | хотя бы одно из `min_date`, `max_date`         | ISO-дата (`YYYY-MM-DD`)                                                                 |
| `duration`   | хотя бы одно из `min_days`, `max_days`         | число с плавающей точкой                                                                |
| `semantic`   | `query` — непустая строка                      | —                                                                                       |

Любое правило с ключами вне этого контракта (например, generic `field`,
`operator`, `unit`, `value`) должно быть **отклонено** с кодом
`invalid_parameters`. Модели запрещено изобретать новые структуры параметров:
промпт должен явно перечислять допустимые ключи для каждого `check_type`.

### 6.4. Provenance правила

Для каждого принятого, отклонённого и дедуплицированного результата нужно
сохранять хотя бы:

- `legal_act_id`;
- `chunk_id`;
- `source_quote`;
- диапазон в тексте НПА;
- модель и preset;
- версию prompt/schema;
- статус (`accepted`, `rejected`, `duplicate`);
- диагностическую причину.

Предпочтительно выделить таблицу `rule_extraction_results`, связанную с
`legal_acts` и `audit_rules`. Если для первого прохода используется JSON,
структура и версия JSON должны быть документированы, а критические поля не
должны быть доступны только внутри неструктурируемой строки.

### 6.5. Состояние НПА

В `legal_acts` или отдельной таблице обработки должны появиться:

- `processing_status`: `uploaded`, `processing`, `completed`, `partial`,
  `failed`;
- `source_language`;
- время начала и завершения;
- количество chunks и правил;
- безопасное диагностическое сообщение;
- `processing_version`.

Состояние `completed` разрешено только если все chunks обработаны, а все
принятые правила прошли валидацию. Если включён offline fallback, это должно
быть отражено отдельным статусом/диагностикой, а не скрыто.

**Схема базы данных:** для хранения нового состояния требуется миграция Alembic
(`0005_legal_act_processing_and_provenance.py`). В ней необходимо:

- добавить поля `processing_status`, `source_language`,
  `processing_started_at`, `processing_finished_at`, `chunks_total`,
  `chunks_processed`, `chunks_failed`, `rules_returned`, `rules_accepted`,
  `rules_rejected`, `processing_version`, `processing_diagnostics` в
  `legal_acts` (или создать отдельную таблицу `legal_act_processing_results`
  с `ForeignKey("legal_acts.id", ondelete="CASCADE")`);
- добавить таблицу `rule_extraction_provenance` со связями на `legal_acts`
  (`ondelete="CASCADE"`) и `audit_rules` (`ondelete="SET NULL"`);
- добавить `CheckConstraint` для статусов НПА по аналогии с
  `ck_documents_status`:
  `"status IN ('uploaded', 'processing', 'completed', 'partial', 'failed')"`.

**Политика повторной обработки:** при повторном запуске извлечения правил для
уже существующего НПА старые сгенерированные правила должны быть полностью удалены (либо деактивированы с учетом частичного уникального индекса `UNIQUE (rule_code) WHERE is_active = TRUE`) в единой транзакции до записи новых. Это гарантирует отсутствие коллизий `rule_code`. Предпочтительно реализовать
отдельный endpoint `POST /api/legal-acts/{id}/reprocess`, а не перегружать
логикой `POST /api/legal-acts/upload`.

## 8. Требования к целостности и ошибкам

- Текст chunk-а и диапазон должны ссылаться на одну и ту же сохранённую версию
  НПА.
- Ошибка одного chunk-а не должна скрывать правила из успешно обработанных
  chunks.
- Ошибка LLM не должна приводить к успешному пустому набору правил без
  диагностики.
- При обязательной online-политике НПА не должен получать `completed`, если
  генерация или публикация правил завершилась ошибкой.
- Сохранение НПА при ошибке extraction допустимо только как явно обозначенный
  `partial`/`failed` результат; API и база должны показывать причину и
  фактические счётчики.
- Невалидная цитата не может стать provenance принятого правила.
- Правило с параметрами, которые не поддерживает validator, не может стать
  активным.
- Нельзя считать количество возвращённых моделью правил количеством созданных
  правил.
- Повторная загрузка одного и того же НПА не должна создавать дубликаты без
  явной версии источника.
- Полные пользовательские тексты, prompt, raw response и секреты нельзя
  писать в логи, ошибки или API-ответы.
- RAG-индекс должен отражать только опубликованный набор правил и не должен
  содержать частично записанную пересборку.

## 9. Критерии готовности

Этап считается завершённым, если:

- большой русскоязычный НПА обрабатывается несколькими chunks без превышения
  лимитов модели;
- каждый chunk имеет проверяемые границы, статью/секцию и стабильный ID;
- каждое принятое правило связано с точной цитатой и provenance;
- английские описания и keywords не принимаются как корректный результат для
  русского НПА без явного диагностического решения;
- количество обработанных, принятых, отклонённых и потерянных результатов
  доступно вызывающему коду и API;
- сбой одного chunk-а даёт диагностируемый `partial`, а не ложный `completed`;
- повторная обработка не создаёт дубликаты и коллизии кодов;
- offline-тесты проходят без сети и API-ключей, но production-конфигурация
  требует доступного онлайн-провайдера;
- regression test подтверждает сохранение детерминированной проверки при сбое
  внешней модели;
- логи не содержат полные НПА, prompt и raw response;
- RAG-индекс пересобирается только из опубликованных и согласованных данных;
- документация описывает ограничения и необходимость ручной юридической
  проверки.

## 10. Команды проверки

Из каталога `backend/` после реализации:

```bash
pytest tests/legal_act_processing -q
pytest tests/api tests/audit_engine tests/rag tests/legal_act_processing -q
pytest -q
```

Пример локального сценария:

```bash
EDM_MODEL_PRESET=offline \
python examples/api_check.py examples/remote_work_agreement.txt \
  --legal-act examples/legal_act_remote_work.txt
```

Этот offline-сценарий предназначен только для тестов и локальной разработки.
Production-сценарий должен использовать выбранный онлайн preset и не должен
переключаться на offline provider при ошибке внешней модели.

Для теста большого НПА следует использовать synthetic fixture с несколькими
статьями и контролируемым fake provider, который возвращает разные правила для
разных chunks и намеренно имитирует сбой одного chunk-а.

## 11. Рекомендуемая последовательность коммитов

```text
docs(config): define legal-act processing stage
build(config): migrate non-secret settings from .env to config/models.toml
feat(db): add legal-act processing status, provenance schema and Alembic migration
feat(config): implement source-preserving legal-act chunking
feat(config): validate rule language and validator parameter contracts
feat(config): extract rules per chunk with rate-limit and retry handling
feat(config): deduplicate and publish generated rules atomically
feat(rag): filter unready legal acts during RAG index build
feat(api): expose legal-act processing diagnostics and reprocess endpoint
feat(ui): display processing status badges and rejected rule diagnostics
test(config): cover partial extraction, HTTP-429 retry and language regressions
docs(config): document legal-act processing workflow and config layout
```

Все изменения выполняются в ветке `feature/audit-configuration`. Этот этап
должен оставаться совместимым с текущими `audit-engine`, FastAPI и offline RAG
для тестового пути, но production-обработка НПА должна считать внешний LLM
обязательным. `EDM_MODEL_PRESET` выбирает онлайн-провайдера, а offline preset
не должен использоваться как скрытый fallback.
