# Журнал разработки EDM-Auditor

Правила ведения описаны в [`AGENTS.md`](../AGENTS.md#development-log).

## Текущее состояние

Курсовой проект БГУИР: аудит электронных документов на соответствие законодательству
Республики Беларусь. Требования описаны в [`docs/TASK.md`](TASK.md). Активная ветка:
`feature/audit-configuration`.

**Работает** (бэкенд на FastAPI, SQLAlchemy и SQLite):

- разбор документов TXT, PDF и DOCX;
- извлечение правил из НПА через LLM, их проверка и атомарная публикация;
- каталог типов документов, определение типа документа и типов каждого правила через LLM,
  предложения новых типов с решением человека;
- выбор применимых правил: режимы `automatic`, `manual`, `combined` и подтверждённый `all`,
  предпросмотр и сохранение конфигурации в отчёте;
- аудит: проверки правил кодом и обязательные вызовы LLM, при сбое модели ответ `503` без отчёта;
  длинные документы читаются частями, все нарушения объясняются пакетами;
- простой веб-интерфейс в `backend/src/edm_auditor/api/web.py`.

**Не сделано:**

- фронтенд на React с подсветкой нарушений, RBAC и другие дополнительные модули из ТЗ;
- выполнение правил типа `semantic` через API: они попадают только в диагностику, а RAG показывает
  лишь рекомендации.

**Известные проблемы:**

- у Google-клиента нет таймаута (`request_timeout_seconds` не передаётся), поэтому запросы могут
  зависать, а при перегрузке Gemini отвечает `503` и аудит падает;
- `load_dotenv` не перезаписывает заданные переменные: если в окружении есть другой
  `GEMINI_API_KEY`, для ключа из `backend/.env` нужен `set -a; source .env; set +a`;
- `alembic.ini` задаёт путь к базе жёстко и не читает `EDM_DATABASE_URL`: миграции всегда идут в
  `data/edm_auditor.sqlite3`;
- один неудачный фрагмент НПА останавливает публикацию всех правил акта: на Трудовом кодексе модель
  дала неточные цитаты и неполные ответы, поэтому большие акты пока не загружаются;
- проверка на 47 фрагментах упёрлась в квоту Gemini (`429`): для больших актов и документов нужна
  пауза `inter_chunk_delay_seconds`;
- порог уверенности 0.7 проверен только на нескольких примерах, а модель почти всегда ставит 0.8–1.0;
- порог RAG-рекомендаций 0.5 выбран без замеров;
- не обновлены `docs/roadmap.md` и пустой корневой `README.md`, также лежит лишний пустой
  `backend/rules.json`.

**Локальные данные** (в Git не входят): в `backend/data/edm_auditor.sqlite3` лежат 3 НПА, 9 правил,
1 документ и 1 отчёт. База ещё не обновлена до `0008_llm_classification` и без таблицы
`alembic_version`, поэтому сервер не запустится, пока не выполнить в `backend/`:
`alembic stamp 0007_rule_applicability && alembic upgrade head`.

## Журнал

### 2026-11-05: типы через LLM и полные запросы к моделям

- Тип документа определяет только LLM по каталогу, признаки и `classifier_profile` удалены. При
  сбое модели документ сохраняется как `pending`, а аудит отвечает `503`, пока тип не получен.
- Типы получает каждое правило при извлечении, модель может объявить его универсальным. Ответ ниже
  порога 0.7 не применяется автоматически: правило `unknown`, документ `needs_review`.
- Новые типы модель только предлагает: `/api/document-type-suggestions` и блок в интерфейсе.
- Сущности извлекаются из всего документа частями, предел `entity_max_chunks` даёт `413`. Все
  нарушения объясняются пакетами; `max_tokens` экстрактора Google поднят до 8192.
- Нужно: миграция `0008_llm_classification` (см. выше). Правила из старых НПА сохраняют типы с
  источником `migration`; новые типы они получат после `reprocess`. Он пересоздаёт правила, поэтому
  нарушения в старых отчётах теряют `rule_id`. См. [`model-configuration.md`](model-configuration.md).
