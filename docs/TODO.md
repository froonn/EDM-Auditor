Мы подробно изучили код движка аудита, экстракторов и провайдеров моделей. Причина, по которой аудит
remote_work_agreement.txt вернул 0 ошибок,
кроется сразу в трёх конкретных архитектурных и логических проблемах.
──────

## 1. Почему так произошло (детальный анализ)

В документе remote_work_agreement.txt заложены 3 ситуации:

1. Срок уведомления: с 25.02.2027 по 01.03.2027 (4 дня вместо положенных 10).
2. Компенсация: 35 рублей (вместо положенных минимум 50 рублей).
3. Словоформы: «дистанционной», «дистанционную».
   Ни одно из трёх правил не сработало по следующим причинам:

### Проблема №1 (Критический баг экстрактора): Проглатывание ошибки Google AI Studio

В правиле №2 (rule-numeric-2) настроена проверка:

    {"entity": "money", "min": 50.0}

В документе чёрным по белому написано: 35 рублей. Это должно было быть найдено на 100%. Почему не нашлось?
• В файле backend/.env включен пресет EDM_MODEL_PRESET=google-ai-studio.
• В GoogleAIStudioEntityExtractionProvider.extract при обращении к Gemini API произошла ошибка (невалидный API-ключ
API_KEY_INVALID):
except Exception as exc:
logger.warning (
"Google AI Studio entity extraction failed (%s); using deterministic extraction",
exc,
)
return ()  # <--- БАГ: вместо фолбэка возвращается пустой кортеж!

• Провайдер вернул (). Из-за этого AuditEngine посчитал, что во всём документе нет вообще никаких сущностей (entities =
()), и блок except (где
вызывается локальный extract_entities) даже не запустился!
• В результате валидатор _numeric_findings перебирал пустой список сущностей и просто не увидел сумму 35 рублей.
──────

### Проблема №2: Несовпадение типов для срока (две даты вместо одного интервала)

Правило №1 (rule-duration-1):
{"check_type": "duration", "parameters": {"min_days": 10}}
• Валидатор _duration_findings ожидает в документе сущность типа duration (явные фразы вида «10 дней», «2 недели», «3
месяца»).
• В тексте договора нет фразы «4 дня» — там стоят две даты: 01.03.2027 и 25.02.2027.
• Они извлекаются как сущности типа date. Валидатор duration не вычисляет разность между двумя произвольными датами
календаря, поэтому сущностей типа
duration в тексте оказалось 0, и проверка не выполнилась.
──────

### Проблема №3: Инверсная логика и падежи в правиле keyword

Правило №3 (rule-keyword-3):
{"check_type": "keyword", "parameters": {"keywords": ["дистанционная"]}}
Здесь двойная нестыковка:

1. Падежи (отсутствие лемматизации): В тексте договора слово употреблено как «дистанционной» и «дистанционную».
   Валидатор _keyword_findings выполняет
   жесткий поиск подстроки re.escape ("дистанционная"). Без морфологического разбора точная форма именительного падежа
   женского рода в документе не
   найдена.
2. Инверсная семантика keyword: В коде _keyword_findings любое найденное ключевое слово порождает нарушение (Finding)
   (так как изначально валидатор
   проектировался для поиска недопустимых условий — например, «штраф», «отпуск 14 дней»). А сгенерированное правило
   требует обратного: «документ обязан
   содержать...». Если бы слово даже нашлось, движок посчитал бы его ошибкой!
   ──────

## 2. Как исправить проблему прямо сейчас

### Шаг 1. Исправить баг в GoogleAIStudioEntityExtractionProvider

В файле model_providers.py:634:
Вместо тихого возврата return () нужно пробрасывать исключение (как это сделано в
OpenAICompatibleEntityExtractionProvider), чтобы управление
переходило в детерминированный экстрактор в engine.py, либо вызывать детерминированный экстрактор напрямую:
except Exception as exc:
logger.warning (
"Google AI Studio entity extraction failed (%s); falling back",
exc,
)
raise ValueError (f"entity extraction provider failed: {exc}") from exc

### Шаг 2. Всегда объединять (Union) нейросетевые сущности с детерминированными в AuditEngine

В AuditEngine.audit:
Детерминированный RegEx-экстрактор работает мгновенно и без сбоев находит числа, деньги (35 рублей) и даты. Нейросетевой
экстрактор должен дополнять
детерминированные сущности, а не заменять их вслепую:
if self._entity_extractor is not None:
try:
provider_entities = self._entity_extractor (text)
entities = _merge_entities (entities, provider_entities)
except Exception as exc:
diagnostics.append (RuleDiagnostic ("entity-extraction", f"provider failed: {exc}"))

### Шаг 3. Добавить поддержку расчета дельты дат и режим must_contain для keyword

• Для правила срока: если в документе дата уведомления и дата вступления в силу, требуется либо валидатор интервала
между датами (date_interval /
date_diff), либо семантический аудит через LLM (check_type="semantic"), где модель понимает контекст обеих дат.
• Для ключевых слов: добавить параметр "mode": "forbidden" (по умолчанию) и "mode": "required", а также регулярное
выражение с основой слова (дистанционн.*).

## 3. Как сделать так, чтобы подобные проблемы больше не появлялись

1. Принцип Fail-safe Hybrid Extraction (Отказоустойчивое извлечение):
   • Сбой или таймаут внешнего LLM-провайдера никогда не должен приводить к потере базовых сущностей (денег, чисел,
   дат).
   • Базовые регулярные выражения должны отрабатывать всегда как фундамент.
2. Схемная валидация и калибровка генерации правил (RuleExtractionProvider):
   • В системный промпт генератора правил из НПА (prompts.py) нужно явно передать спецификацию валидаторов:
   • keyword — используется только для поиска запрещенных формулировок, либо использовать regex дистанционн[а-я]*.
   • duration — применяется только если в тексте ожидается фраза с количеством дней/месяцев. Для соотношения дат должен
   генерироваться semantic
   или date_order.

3. Автоматизированные сквозные регрессионные тесты (Gold Dataset):
   • Добавить в тестовый набор тест, который берет пару legal_act_remote_work.txt + remote_work_agreement.txt, извлекает
   правила и проверяет, что
   количество найденных нарушений строго > 0. Если при невалидном API-ключе тесты вернут 0 ошибок — сборка падает.
