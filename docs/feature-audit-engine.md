# План разработки: `feature/audit-engine`

> **Статус:** в реализации. Контракты, извлечение сущностей, детерминированные
> keyword/regex/numeric-проверки и атомарное сохранение отчётов реализованы.
> RAG-контекст, синтетические fixtures и optional Natasha adapter остаются
> следующими задачами. Конфигурация embedding/LLM-провайдеров подготовлена, но
> LLM пока не является частью обязательного audit pipeline.

## 1. Назначение этапа

Реализовать детерминированный движок проверки пользовательских документов по
активным правилам аудита. Движок должен находить проверяемые нарушения,
сохранять координаты и цитаты исходного текста, связывать результат с правилом
и НПА, а затем сохранять единый `AuditReport` в database layer.

LLM-проверки, если они понадобятся для семантических коллизий, должны быть
отдельным опциональным адаптером. Базовый путь аудита не должен требовать сети,
API-ключей или production embedding provider.

## 2. Цели и результат

После завершения этапа система должна:

1. Получать документ из database layer вместе с нормализованным текстом и
   абзацами.
2. Выбирать активные правила, применимые к типу документа.
3. Извлекать из текста проверяемые сущности: даты, сроки, суммы, проценты,
   стороны и другие значения, нужные правилам.
4. Выполнять детерминированные проверки по keyword, regex и параметрам правила.
5. Использовать RAG-поиск для получения релевантных фрагментов НПА без
   самостоятельного юридического вывода.
6. Возвращать нормализованные findings с severity, описанием, цитатой,
   диапазоном текста, правилом и источником НПА.
7. Создавать отчёт с агрегированными счётчиками по уровням severity.
8. Сохранять отчёт атомарно и обновлять статус документа.
9. Давать одинаковый результат для одинакового текста, правил и конфигурации.

## 3. Границы этапа

### Входит в этап

- контракты audit engine, extractor, validator и finding;
- детерминированный pipeline обработки документа;
- извлечение сущностей через стандартную библиотеку, регулярные выражения и
  опциональный Natasha-адаптер;
- keyword- и regex-проверки;
- параметризованные проверки сроков, дат, чисел и минимальных значений;
- интеграция с `RAGSearch` для получения контекста НПА;
- преобразование результатов в `AuditReport` и `AuditFinding`;
- репозиторные операции для сохранения отчёта;
- unit- и integration-тесты на временной SQLite-базе;
- небольшие синтетические fixtures документов, правил и НПА;
- документация запуска и ограничений.

### Не входит в этап

- FastAPI endpoints и авторизация;
- React frontend и визуальная подсветка;
- обязательный внешний LLM или production embedding provider;
- OCR и новые форматы документов;
- автоматическая юридическая экспертиза или утверждение соответствия закону;
- генерация окончательных юридических заключений;
- загрузка полного корпуса нормативных актов;
- фоновые очереди и распределённое выполнение аудита.

## 4. Предлагаемая структура модулей

```text
backend/
  src/edm_auditor/audit_engine/
    __init__.py
    models.py          # AuditRequest, FindingDraft, AuditResult
    exceptions.py      # явные ошибки pipeline и конфигурации
    extractors.py      # даты, числа, сроки и текстовые сущности
    validators.py      # keyword, regex и параметризованные проверки
    rag_validator.py   # поиск нормативного контекста через RAG
    engine.py          # orchestration и детерминированный pipeline
    persistence.py     # сохранение отчёта и статуса документа
  tests/audit_engine/
    test_extractors.py
    test_validators.py
    test_engine.py
    test_persistence.py
```

Названия модулей можно изменить при реализации, но domain-код не должен
зависеть от SQLAlchemy-моделей, CLI или конкретного embedding provider.

## 5. Контракты и модель данных

### 5.1. Запрос аудита

Запрос должен содержать как минимум:

- `document_id`;
- необязательный `document_type`;
- идентификаторы правил или режим выбора активных правил;
- настройки порогов и RAG, если они нужны;
- идентификатор запуска или возможность идемпотентной повторной обработки.

### 5.2. Finding draft

Промежуточный результат проверки должен содержать:

- код и идентификатор правила;
- severity;
- краткое описание нарушения;
- `start_char` и `end_char` исходного текста либо явное отсутствие диапазона;
- точную цитату `document.raw_text[start_char:end_char]`, если диапазон есть;
- `legal_act_id` и RAG-цитату при наличии нормативного контекста;
- рекомендацию, если она сформулирована детерминированным правилом;
- стабильный ключ дедупликации.

До сохранения результата необходимо проверять, что диапазон не выходит за
границы `raw_text`, а цитата соответствует указанному диапазону.

### 5.3. Audit report

На уровне domain-модели отчёт должен включать:

- идентификатор документа;
- список findings;
- количество findings всего и по severity;
- краткое техническое summary;
- время и статус выполнения;
- диагностические ошибки, если отдельное правило не удалось выполнить.

Существующие таблицы `audit_reports` и `audit_findings` являются целевым
слоем хранения. Если их полей недостаточно для трассировки источника или
ошибок, сначала подготовить отдельную миграцию и обновить модели.

## 7. Требования к целостности и ошибкам

- Диапазоны findings должны ссылаться на исходный `Document.raw_text`.
- Цитата finding должна совпадать с текстом по диапазону.
- Неактивные правила не должны запускаться.
- Правило, предназначенное для другого типа документа, не должно применяться
  без явно заданного режима override.
- Ошибки regex, параметров и extractor должны быть диагностируемыми.
- Ошибка отдельного правила не должна приводить к успешному пустому отчёту.
- Ошибка сохранения не должна оставлять частичный `AuditReport`.
- Нельзя записывать в логи полные пользовательские документы или секреты.
- RAG-результат должен сохранять ссылку на НПА и score, если он использован.
- LLM и внешняя сеть не должны быть обязательными для unit- и integration-тестов.

## 8. Критерии готовности

Этап считается завершённым, если:

- документ можно проверить одной внутренней командой без FastAPI;
- активные правила выбираются по типу документа;
- keyword и regex rules создают findings с корректными диапазонами;
- числовые и временные ограничения проверяются детерминированно;
- findings связаны с правилами и нормативными источниками;
- отчёт и findings сохраняются атомарно;
- статус документа отражает результат выполнения;
- повторный аудит имеет документированное идемпотентное поведение;
- тесты проходят без сети, API-ключей и реального корпуса НПА;
- документация описывает ограничения и необходимость юридической проверки;
- подключение LLM остаётся опциональным и не меняет базовый контракт.

## 9. Команды проверки

Из каталога `backend/` после реализации:

```bash
pytest tests/audit_engine -q
pytest tests/database tests/rag tests/audit_engine -q
```

Для ручной проверки планируется отдельная команда или Python API. Она должна
показывать только структурированный результат: severity, rule code, описание,
цитату, диапазон документа и нормативный источник.
