# План разработки: `feature/rag-indexer`

> **Статус:** основная offline-реализация завершена. Открыты только задачи,
> требующие отдельного решения или данных: production embedding provider,
> стартовый fixture-датасет и дополнительные негативные тесты.

Production embedding provider и стартовый датасет нормативных актов в текущей
ветке **не реализованы**. Для обязательного тестового пути используется только
`DeterministicEmbeddingProvider`, а реальные тексты НПА должны подключаться
отдельно после выбора разрешённого источника данных.

## 1. Назначение этапа

Реализовать подготовку и поиск фрагментов нормативных документов, которые
понадобятся `audit-engine` для проверки пользовательских документов. Индекс
должен связывать каждый найденный фрагмент с исходным нормативным актом,
правилом и координатами текста, чтобы результат поиска можно было проверить и
показать пользователю.

Результатом этапа является отдельный RAG/indexing layer с детерминированным
chunking, интерфейсом embedding-провайдера, локальным векторным хранилищем,
поиском по порогу сходства и тестами без обязательного доступа к внешнему
LLM-сервису.

## 2. Цели и результат

После завершения этапа система должна:

1. Принимать тексты нормативных актов из database layer и превращать их в
   последовательность неперекрывающихся или контролируемо перекрывающихся
   фрагментов.
2. Сохранять для каждого фрагмента исходный текст, стабильный идентификатор,
   ссылку на НПА/правило и диапазон символов в исходном тексте.
3. Получать embedding через заменяемый провайдер, не связывая доменный код с
   конкретным API или моделью.
4. Индексировать фрагменты и выполнять top-k поиск с минимальным порогом
   сходства.
5. Возвращать результаты в детерминированном порядке вместе с метаданными,
   необходимыми для цитирования и дальнейшего аудита.
6. Позволять полностью пересоздать локальный индекс из базы данных.
7. Работать в тестах с детерминированным fake embedding provider.
8. Документировать настройку модели, индекса и команды проверки.

## 3. Границы этапа

### Входит в этап

- контракты chunker, embedding provider, vector store и search service;
- нормализация и разбиение текста нормативных актов;
- сохранение chunk metadata и связи с `legal_acts`/`audit_rules`;
- локальное векторное хранилище, подходящее для текущего SQLite-based проекта;
- построение индекса и его повторная синхронизация;
- top-k семантический поиск с фильтрами и threshold;
- fake embedding provider и unit-/integration-тесты;
- документация установки, индексации и поиска.

### Не входит в этап

- загрузка нормативных актов через FastAPI;
- OCR и парсинг новых форматов документов;
- генерация текста, исправлений или юридических выводов LLM;
- выполнение правил аудита и формирование `audit_reports`;
- автоматический выбор релевантных правил;
- frontend и пользовательский интерфейс;
- обязательная интеграция с платным или удалённым embedding API;
- импорт полного набора реальных нормативных актов и юридическая экспертиза
  их содержания.

Конкретная реализация векторного хранилища должна быть выбрана до добавления
зависимостей. Для текущего этапа предпочтителен локальный вариант без отдельного
сервера (например, SQLite metadata + файловый/локальный vector index). API
модулей не должен зависеть от внутреннего формата выбранного хранилища, чтобы
позднее можно было заменить его на Qdrant, pgvector или другой backend.

## 5. Контракты и модель данных

### 5.1. Chunk

Каждый chunk должен содержать:

- стабильный `chunk_id`, производный от идентификатора НПА, версии текста и
  порядкового номера;
- `legal_act_id` и необязательный `rule_id`;
- исходный `text` без потери значимых пробелов внутри фрагмента;
- `chunk_index` в пределах исходного текста;
- `start_char` и `end_char`;
- версию chunking-конфигурации;
- embedding и имя embedding-модели в индексе, но не в качестве части текста.

Должен выполняться контракт:

```python
source_text[start_char:end_char] == chunk.text
```

Если chunk строится из отдельных статей или секций, их заголовки должны
сохраняться в тексте фрагмента либо в явно описанных метаданных. Нельзя
терять ссылку на статью, пункт или другой источник цитаты.

### 5.2. Chunking

В начале этапа зафиксировать:

- целевой размер chunk в токенах или символах;
- размер overlap;
- правила разбиения по заголовкам, абзацам и предложениям;
- поведение для пустого текста и текста, меньшего одного chunk;
- максимальную длину, при которой создаётся дополнительное разбиение;
- нормализацию переносов строк и пробелов.

Для первой версии использовать детерминированный paragraph-aware chunker:
сначала сохранять границы секций/абзацев, затем объединять соседние абзацы до
целевого размера, не разрезая слово без необходимости. Overlap должен быть
ограничен и измерим, а диапазоны в исходном тексте должны вычисляться до
нормализации или иметь явно документированное соответствие.

### 5.3. Embedding provider

Определить типизированный интерфейс примерно со следующими операциями:

```python
embed_documents(texts: Sequence[str]) -> Sequence[Vector]
embed_query(text: str) -> Vector
```

Провайдер обязан:

- возвращать векторы одинаковой размерности;
- явно сообщать об ошибке сети, конфигурации или несовместимой размерности;
- поддерживать пакетную обработку документов;
- фиксировать имя и размерность модели;
- не хранить ключи API в коде или Git.

В основную тестовую конфигурацию включить deterministic fake provider. Реальный
провайдер подключать через optional dependency или конфигурацию, чтобы unit-
тесты не зависели от сети и внешних секретов.

### 5.4. Vector store и поиск

Интерфейс vector store должен поддерживать:

- создание или открытие индекса с проверкой размерности и модели;
- upsert по стабильному `chunk_id`;
- удаление chunks, отсутствующих в новой сборке;
- получение количества записей и очистку индекса;
- top-k поиск по query vector;
- фильтрацию по `legal_act_id`, `rule_id` и другим поддержанным метаданным.

Результат поиска должен включать `chunk_id`, score, текст и все source metadata.
Сортировка при одинаковом score должна быть стабильной, например по
`chunk_id`. Невалидный `k`, threshold вне диапазона `[-1, 1]`, пустой запрос и
несовместимая размерность должны приводить к явной ошибке, а не к пустому
успешному результату.

## 7. Требования к целостности и ошибкам

- Индекс нельзя считать готовым, если для части chunks не созданы embeddings.
- Нельзя смешивать в одном индексе векторы с разными моделями или размерностями
  без явной поддержки версий.
- Повторная индексация не должна создавать дубликаты при неизменном
  `chunk_id`.
- Ошибка embedding provider или vector store должна быть явно возвращена
  вызывающему коду и не маскироваться пустым списком результатов.
- Удаление или изменение нормативного акта должно удалять либо заменять его
  устаревшие chunks.
- Каждый search result должен сохранять ссылку на исходный НПА и координаты
  фрагмента.
- Секреты и содержимое внешних пользовательских документов не должны
  записываться в логи или коммититься в репозиторий.
- Индекс и тестовые артефакты должны храниться вне Git либо быть добавлены в
  `.gitignore`; исходный код схемы и миграций игнорироваться не должен.

## 8. Критерии готовности

Этап считается завершённым, если:

- нормативный акт из database layer индексируется одной документированной
  командой;
- для каждого chunk сохраняются текст, source metadata, диапазоны и версия
  chunking-конфигурации;
- индекс можно полностью пересоздать без ручного редактирования файлов;
- поиск возвращает top-k релевантных chunks с score и проверяемым источником;
- filters и threshold работают согласно документированному контракту;
- повторная индексация не создаёт дубликаты и удаляет устаревшие chunks;
- смена embedding-модели обнаруживается до чтения несовместимых векторов;
- тесты проходят без сети, API-ключей и реального корпуса документов;
- документация объясняет установку, индексацию, поиск и ограничения решения;
- функциональность не требует FastAPI, frontend или `audit-engine`.

## 9. Команды проверки

Из каталога `backend/` после реализации:

```bash
pytest tests/rag -q
```

Для проверки конкретного локального сценария:

```bash
python -m edm_auditor.rag --help
python -m edm_auditor.rag search --help
```

Названия CLI-команд должны быть скорректированы после выбора окончательной
структуры модулей и добавлены в `backend/README.md`. Если будет выбран внешний
провайдер, основная проверка должна использовать fake provider, а интеграционный
тест с сетью — запускаться отдельно и явно.

## 10. Рекомендуемая последовательность коммитов

```text
docs(rag): add indexer implementation plan
build(rag): add indexing dependencies
feat(rag): define chunk and embedding contracts
feat(rag): implement deterministic document chunking
feat(rag): add local vector store
feat(rag): build index and semantic search
test(rag): cover indexing and retrieval
docs(rag): document indexer setup and usage
```

Все изменения этапа выполняются в ветке `feature/rag-indexer`. Этап должен
завершиться независимым от FastAPI и frontend RAG layer, который предоставляет
`audit-engine` типизированный поиск нормативных фрагментов и проверяемые
источники.
