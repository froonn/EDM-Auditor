# План разработки: `feature/document-parser`

## 1. Назначение этапа

Реализовать первый прикладной модуль `EDM-Auditor`, который принимает документы
`.docx` и `.pdf`, извлекает из них текст и базовую структуру, а также сохраняет
результат в форме, пригодной для последующего аудита, поиска и подсветки
нарушений.

Этап не включает юридическую проверку документа, NER, RAG, LLM, REST API и
пользовательский интерфейс. Его результатом является стабильный внутренний
контракт парсера, которым смогут пользоваться следующие этапы разработки.

## 2. Цели и результат

После завершения этапа система должна:

1. Принимать локальный файл `.docx` или `.pdf`.
2. Определять формат по расширению и проверять, что файл действительно
   поддерживается.
3. Извлекать текст с сохранением порядка блоков и абзацев.
4. Сохранять метаданные документа: имя файла, MIME-тип, размер и время
   обработки.
5. Разбивать текст на абзацы с последовательными индексами и позициями
   символов в нормализованном общем тексте.
6. Возвращать понятные ошибки для неподдерживаемого, повреждённого и
   недоступного файла.
7. Давать одинаковый формат результата для DOCX и PDF.

## 3. Границы этапа

### Входит в этап

- модуль извлечения текста из DOCX через `python-docx`;
- модуль извлечения текста из PDF через `pypdf` или `pdfplumber`;
- единая модель результата парсинга;
- нормализация пробелов и переводов строк без изменения содержимого слов;
- индексация абзацев и позиций символов;
- обработка пустых страниц и документов без текстового слоя;
- unit- и integration-тесты на обычных и ошибочных файлах;
- краткая документация публичного интерфейса модуля.

### Не входит в этап

- OCR для сканированных PDF;
- извлечение таблиц, изображений, подписей и вложенных файлов как отдельных
  объектов;
- юридическая классификация и проверка содержания;
- выделение сущностей, реквизитов и дат;
- хранение в SQLite;
- HTTP endpoints и загрузка через frontend.

PDF без текстового слоя должен распознаваться как корректный, но
необрабатываемый текущей версией документ с явным статусом или ошибкой
`text_layer_required`. Это позволит добавить OCR позднее без изменения
контракта парсера.

## 4. Предлагаемая структура модулей

```text
backend/
  pyproject.toml
  src/
    edm_auditor/
      document_parser/
        __init__.py
        models.py       # DocumentMetadata, ParsedDocument, ParsedParagraph
        exceptions.py   # публичные ошибки парсинга
        base.py         # протокол/абстракция parser
        docx_parser.py
        pdf_parser.py
        service.py      # выбор парсера и единая точка входа
  tests/
    fixtures/
      documents/
        simple.docx
        simple.pdf
        empty.pdf
        corrupted.pdf
    document_parser/
      test_docx_parser.py
      test_pdf_parser.py
      test_service.py

frontend/
  package.json
  src/
```

Исходники backend и frontend находятся в отдельных приложениях. Код парсера
размещается в `backend/src/edm_auditor/document_parser/`, а тесты — в
`backend/tests/document_parser/`. Frontend на этом этапе не изменяется.
Ответственность модулей должна оставаться разделённой: форматный парсер
извлекает данные, а `service.py` выбирает нужную реализацию и выполняет общую
валидацию результата.

## 5. Внутренний контракт результата

Рекомендуемая модель результата:

```python
ParsedDocument(
    source=DocumentMetadata(
        filename="contract.docx",
        media_type="application/vnd.openxmlformats-officedocument.wordprocessingml.document",
        size_bytes=12345,
        format="docx",
    ),
    text="Первый абзац.\n\nВторой абзац.",
    paragraphs=[
        ParsedParagraph(
            index=0,
            text="Первый абзац.",
            start_char=0,
            end_char=13,
            page_number=None,
        ),
        ParsedParagraph(
            index=1,
            text="Второй абзац.",
            start_char=15,
            end_char=28,
            page_number=None,
        ),
    ],
)
```

Требования к контракту:

- `text` — единый нормализованный текст документа;
- `paragraphs` — непустые логические блоки в порядке появления;
- `start_char` включителен, `end_char` исключителен;
- позиции считаются относительно `text`, а не исходного бинарного файла;
- `page_number` заполняется для PDF и остаётся `None` для DOCX, если
  надёжное соответствие страниц недоступно;
- индексы абзацев начинаются с нуля и не имеют пропусков;
- пустые абзацы не создают элементы результата, если это не требуется для
  сохранения таблиц или иной структуры.

Перед публикацией интерфейса нужно выбрать одну библиотеку для PDF и
зафиксировать её в зависимостях. Если извлечение обычного текста и страниц
надёжно покрывается `pypdf`, предпочтительно начать с него; `pdfplumber`
следует добавлять только при подтверждённой потребности в более сложной
структуре.

## 7. Требования к ошибкам

Публичные ошибки должны позволять вызывающему коду отличить:

- `UnsupportedDocumentFormat` — формат не поддерживается;
- `DocumentNotFound` или `DocumentAccessError` — файл недоступен;
- `InvalidDocument` — файл повреждён или не соответствует формату;
- `TextLayerRequired` — PDF прочитан, но текстовый слой отсутствует;
- `DocumentTooLarge` — превышено установленное ограничение размера.

Нельзя молча возвращать пустой успешный результат для повреждённого файла или
сканированного PDF. Сообщение ошибки должно быть безопасным для показа
пользователю и не содержать полный текст документа или чувствительные данные.

## 8. Критерии готовности

Этап считается завершённым, если:

- DOCX и PDF с текстовым слоем дают непустой `ParsedDocument`;
- порядок абзацев и страниц сохраняется;
- каждый абзац имеет корректный диапазон в общем `text`;
- `text[start_char:end_char] == paragraph.text` для всех абзацев;
- поддерживаются русские и латинские символы, даты и денежные значения;
- повреждённые, пустые и неподдерживаемые файлы обрабатываются предсказуемо;
- тесты покрывают успешные сценарии и все публичные типы ошибок;
- парсер не зависит от FastAPI, SQLite, LLM и frontend;
- публичные модели и способ запуска задокументированы.

## 9. Стратегия тестирования

Минимальный набор проверок:

1. Unit-тесты нормализации текста и расчёта диапазонов.
2. Unit-тесты DOCX-парсера.
3. Unit-тесты PDF-парсера с проверкой `page_number`.
4. Integration-тест единого сервиса для обоих расширений.
5. Тесты ошибок: неизвестное расширение, отсутствующий файл,
   повреждённый файл, PDF без текстового слоя.
6. Регрессионные фикстуры для документов с кириллицей и таблицами.

Команда проверки должна быть указана в `pyproject.toml`; ожидаемый вариант:

```bash
cd backend
pytest tests/document_parser -q
```

## 11. Результат для следующих этапов

Следующие модули должны использовать только единый `ParsedDocument`, а не
напрямую вызывать `python-docx` или PDF-библиотеку. Это позволит аналитическому
модулю работать с документом независимо от исходного формата и использовать
диапазоны `start_char`/`end_char` для подсветки найденных нарушений в интерфейсе.
