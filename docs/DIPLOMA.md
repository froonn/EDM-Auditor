# Требования к дипломному проекту

Сюда записывается то, что осознанно перенесено из курсового проекта в дипломный. Формулировки требований FR
находятся в [`TASK.md`](TASK.md), а здесь описано, что к ним уже готово и что нужно сделать. Список пополняется
по мере работы над курсовым.

## 1. Перенесённые требования

### Авторизация и роли (FR-6.3)

Роли: `Администратор` управляет НПА и правилами, `Юрист / Аудитор` проводит полный аудит и пишет резолюции,
`Сотрудник / Кадровик` загружает и создаёт документы.

**Уже есть:**

- таблица `users` с ролями `admin`, `auditor`, `hr` и поле `documents.user_id`. API их пока не использует;
- интерфейс подготовлен: права, единый клиент API и обработка `401` и `403`, см. раздел 4 в
  [`feature-frontend.md`](feature-frontend.md).

**Нужно сделать:**

- [ ] **В начале работы над дипломом** определить таблицу прав: какие права есть у каждой роли. Например, запускает
  ли кадровик аудит. Курсовой задаёт только список прав без привязки к ролям.
- [ ] Выбрать способ входа (cookie-сессия или токены) и описать причину выбора.
- [ ] Реализовать вход, выход, хранение паролей и управление пользователями.
- [ ] Проверять права **на сервере** на каждом эндпоинте: скрытая кнопка в интерфейсе не является защитой.
- [ ] Определить доступ к данным: видит ли кадровик только свои документы и отчёты. Сейчас `user_id` не
  заполняется, и старые документы останутся без владельца.
- [ ] Защитить журнал `data/debug.log` и файлы загрузок: в журнал попадают тела запросов, в том числе текст
  документов.
- [ ] Настроить запуск вне доверенной среды: сейчас API не защищён и работает только локально.
- [ ] Реализовать в интерфейсе вход, меню пользователя и таблицу прав.
- [ ] Реализовать резолюции аудитора: сейчас такой сущности нет.

### Семантический аудит (FR-3.2)

**Уже есть:** RAG-индекс и поиск, RAG показывает рекомендации при выборе правил, а тип `semantic` остался в
перечислении, но модель и API не могут создать такие правила.

**Нужно сделать:**

- [ ] Выполнять правила `semantic` через RAG и языковую модель.
- [ ] Находить требования без сравниваемого значения: «один раз в месяц» при норме «не реже двух раз в месяц».
- [ ] Находить признаки трудовых отношений в договоре подряда (критерий приёмки из `TASK.md`).
- [ ] Измерить качество на размеченном наборе документов и выбрать порог RAG: значение 0.5 выбрано без замеров.

### Извлечение фактов (FR-2)

**Уже есть:** извлечение сущностей (даты, суммы, сроки, проценты) для проверок.

### Конструктор кадровых документов (FR-6.1)

при вводе. **Пока ничего не сделано.** Проверка при вводе может использовать существующие правила аудита.

### Электронная цифровая подпись (FR-6.2)

Проверка или эмуляция подписи: целостность файла, статус сертификата, штамп времени. **Пока ничего не сделано.**
Нужно решить, будет ли это настоящая проверка или эмуляция.

### Готовый фрагмент для вставки (FR-4.3)

Кнопка «Скопировать готовый фрагмент» в карточке замечания.

**Нужно сделать:**

- [ ] Добавить в ответ модели необязательное поле `suggested_text` с текстом для вставки и проверять его при разборе.
- [ ] Отдавать поле в `neural_analyses`. У отчётов без него кнопка не показывается.

### Язык интерфейса и цветовая тема

Переключение языка интерфейса и цветовой темы, например, тёмной.

**Уже есть:** интерфейс курсового берёт тексты из словаря, а цвета из переменных CSS, см. раздел 4а в
[`feature-frontend.md`](feature-frontend.md).

**Нужно сделать:**

- [ ] Выбрать языки, добавить словари и переключатель, сохранять выбор пользователя.
- [ ] Решить, на каком языке модель пишет пояснения: на языке документа или на языке интерфейса.
- [ ] Выгружать отчёт на языке интерфейса: тексты файла лежат в `backend/src/edm_auditor/report_export/labels.py`,
  нужен словарь на каждый язык и параметр языка у `GET /api/reports/{id}/export`.
- [ ] Добавить тёмную тему, учитывать системную настройку и сохранять выбор.
- [ ] Проверить контраст цветов подсветки нарушений в каждой теме.

### Подтверждение выполненных правил

На экране аудита показывать, какой фрагмент документа подтверждает выполнение правила: например, найденное
обязательное слово или значение в пределах нормы.

**Уже есть:** экран аудита по кнопке показывает правила без нарушений. Список берётся из сохранённого набора
правил отчёта.

**Нужно сделать:**

- [ ] Сохранять в отчёте для каждого выполненного правила найденный фрагмент и его позицию. Сейчас движок
  аудита запоминает только нарушения.
- [ ] Подсвечивать эти фрагменты отдельным цветом и связывать их с правилом, как нарушения.
- [ ] Решить, что показывать для правил, которые выполнены из-за отсутствия значения, например, запретного слова.

### Экспорт отчёта в PDF и DOCX (FR-4.4)

FR-4.4 требует экспорт в PDF или HTML либо размеченный DOCX с комментариями.

**Уже есть:** `GET /api/reports/{id}/export?format=html` и кнопка «Скачать HTML» на экране аудита. Файл
содержит стили, открывается без сети, и браузер может распечатать его или сохранить в PDF. Форматы
подключаются в `backend/src/edm_auditor/report_export/`, поэтому API и интерфейс не меняются: кнопка
появляется для каждого значения `EXPORT_FORMATS` в `frontend/src/api/types.ts`.

**Нужно сделать:**

- [ ] **PDF на сервере.** Например, WeasyPrint из того же HTML. Проверить русские шрифты в Docker, переносы
  страниц внутри карточек и размер образа: WeasyPrint требует системных библиотек.
- [ ] **DOCX с комментариями.** Для DOCX-документа добавлять комментарии Word к фрагментам нарушений в копию
  исходного файла. Смещения отчёта указывают на текст парсера, поэтому нужно сопоставить их с абзацами и
  фрагментами `python-docx`, а для TXT и PDF создавать новый DOCX из текста. В `python-docx` комментарии
  появились недавно, версию и поддержку нужно проверить.
- [ ] Решить, нужен ли выбор разделов отчёта, например, без текста документа или без правил без нарушений.
- [ ] Ограничить экспорт правом `reports.export` на сервере, см. раздел про роли.

## 2. Кандидаты

По этим пунктам решение ещё не принято: они отложены в [`TODO.md`](TODO.md) и могут быть решены и в курсовом.

- **Большие НПА.** Один неудачный фрагмент останавливает публикацию всех правил, а лимит модели быстро
  исчерпывается. Нужны частичная публикация и очередь запросов.
- **Долгие операции.** Загрузка НПА и аудит выполняются одним запросом без прогресса. Для больших файлов нужны
  фоновые задачи.
- **Повторная обработка НПА** теряет ручные правки правил.
- **Настройки без эффекта:** `max_prompt_chars`, `max_response_tokens`, `max_rules_per_chunk`.
- **`alembic.ini`** задаёт путь к базе жёстко и не читает `EDM_DATABASE_URL`.
