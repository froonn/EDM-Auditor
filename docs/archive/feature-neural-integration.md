# План разработки: `feature/neural-integration`

> **Статус:** в работе. Базовые адаптеры `EmbeddingProvider` и `LLMProvider`,
> конфигурация профилей, структурированный LLM interpreter и offline-провайдеры
> реализованы. Остаются production embedding, корпус НПА и smoke-тесты.

## 1. Назначение этапа

Подключить нейросетевые компоненты к существующему аудиту документов:

1. production-совместимые embeddings должны использоваться для индексации и
   поиска фрагментов НПА;
2. LLM должна интерпретировать результаты детерминированных проверок и
   найденный нормативный контекст;
3. API должен возвращать структурированный результат нейросетевого анализа;
4. отказ, таймаут или некорректный ответ внешней модели не должны приводить к
   ложному успешному аудиту или потере детерминированных findings.

LLM в этой версии является вспомогательным аналитическим слоем. Она не имеет
права самостоятельно объявлять документ соответствующим законодательству и не
заменяет проверяемые правила или юридическую экспертизу.

## 2. Цели и результат

После завершения этапа система должна:

- загружать выбранный preset из `backend/config/models.toml`;
- строить и обновлять RAG-индекс через выбранный embedding-провайдер;
- проверять совместимость размерности embedding-векторов и версии индекса;
- передавать LLM только необходимые findings и релевантные фрагменты НПА;
- получать от LLM строго валидируемый JSON по зафиксированной схеме;
- сохранять объяснение, рекомендации и диагностический статус в отчёте;
- явно отличать результаты `deterministic`, `rag` и `llm`;
- работать с LM Studio и другими OpenAI-compatible API;
- предоставлять безопасный offline fallback для тестов;
- не раскрывать в логах документы, API-ключи и полные ответы провайдера.

## 3. Границы этапа

### Входит в этап

- подключение `EmbeddingProvider` к CLI и audit pipeline;
- индексация реального набора НПА и проверка качества поиска;
- контракт LLM-входа и структурированного LLM-выхода;
- сервис интерпретации findings и RAG-контекстов;
- валидация, ограничение размера и дедупликация ответа модели;
- конфигурируемая политика ошибок и таймаутов;
- интеграция с `AuditPersistence` и FastAPI report endpoint;
- offline, mock и opt-in integration-тесты;
- документация запуска с LM Studio и OpenRouter.

### Не входит в этап

- обучение или дообучение собственной модели;
- автоматическое утверждение юридического соответствия;
- OCR и новые форматы документов;
- авторизация, RBAC и владение документами;
- фоновые очереди и распределённое выполнение;
- отправка всего документа внешнему провайдеру без явной настройки;
- замена детерминированных правил выводами LLM.

## 4. Архитектура

```text
document
  -> deterministic AuditEngine
  -> RAGSearch(EmbeddingProvider)
  -> LLMInterpreter(LLMProvider)
  -> validated NeuralAnalysis
  -> AuditReport.summary / API response
```

Доменный код должен зависеть от протоколов, а не от `urllib`, LM Studio,
OpenRouter или конкретной библиотеки модели:

```text
audit_engine/
  neural_models.py       # контракты запроса, ответа и статуса
  llm_interpreter.py     # prompt assembly, provider call, validation
  prompts.py             # версионируемые system/user prompt templates
  neural_errors.py       # timeout, invalid response, provider errors
```

`model_providers.py` остаётся транспортным адаптером. Он не должен содержать
юридическую логику, формировать findings или менять результаты правил.

## 5. Контракты

### 5.1. Запрос к LLM

Запрос должен содержать только необходимые данные:

- идентификатор и версию prompt schema;
- структурированные findings;
- цитаты документа, ограниченные размером;
- RAG-контексты с `legal_act_id`, score и диапазоном источника;
- тип документа и безопасные диагностические метаданные.

Для каждого finding нужно сохранять ссылку на его `rule_code` и диапазон
исходного текста. Нельзя просить модель анализировать произвольный текст,
если он не связан с finding или нормативным контекстом.

### 5.2. Ответ LLM

Ожидаемый JSON-контракт:

```json
{
  "schema_version": "1",
  "status": "ok",
  "analyses": [
    {
      "finding_key": "RULE-001:10:32",
      "explanation": "Краткое объяснение риска",
      "recommendation": "Проверить и уточнить условие договора",
      "confidence": 0.82,
      "legal_basis": [
        {"legal_act_id": 1, "quote": "Релевантный фрагмент НПА"}
      ]
    }
  ],
  "general_summary": "Техническое резюме результатов"
}
```

`finding_key`, `confidence` и ссылки на НПА должны проверяться приложением.
Невалидные, неизвестные или лишние ссылки не должны превращаться в новые
findings. Некорректный ответ должен дать диагностическую ошибку и сохранить
детерминированные результаты.

### 5.3. Состояния анализа

Нужно различать:

- `not_requested` — LLM отключена;
- `completed` — ответ принят и прошёл валидацию;
- `failed` — провайдер недоступен или вернул ошибку;
- `invalid_response` — ответ получен, но не соответствует контракту.

Статус и диагностика сохраняются в `AuditReport.summary`; отсутствие LLM не
должно скрываться успешным текстом без статуса.

## 7. Безопасность и качество результата

- Никогда не хранить ключи в `models.toml`, `.env.example`, Git или отчётах.
- Не передавать в облачную модель полный документ, если для анализа достаточно
  цитаты и RAG-контекста.
- Ограничить размер цитат, контекстов и общего prompt.
- Считать вывод модели недоверенным вводом: валидировать JSON, ссылки и длины.
- Не принимать от LLM новые severity, legal act IDs или диапазоны без
  соответствия данным приложения.
- Не логировать raw document, prompt, API-ключи и полный ответ модели.
- Разделять техническую уверенность модели и юридическую достоверность.
- Сохранять provenance: модель, preset, индекс, prompt version и timestamp.
- При изменении embedding-модели пересобирать индекс, а не смешивать векторы.

## 8. Критерии готовности

Этап считается завершённым, если:

- offline-тесты проходят без сети и API-ключей;
- RAG использует выбранную embedding-модель и проверяет размерность;
- LLM вызывается только через `LLMProvider`;
- валидный ответ модели сохраняется в структурированном отчёте;
- невалидный или недоступный LLM не скрывает детерминированные findings;
- режим `required` не создаёт ложный успешный аудит;
- FastAPI возвращает neural status и diagnostics без секретов;
- повторный аудит воспроизводим при фиксированных моделях, prompt и индексе;
- есть opt-in smoke-тест с реальным OpenAI-compatible сервером;
- документация описывает ограничения и необходимость юридической проверки.

## 9. Команды проверки

Из каталога `backend/`:

```bash
pytest tests/model_providers tests/rag tests/audit_engine -q
pytest -q

EDM_MODEL_PRESET=lm-studio python -m edm_auditor.rag build
EDM_MODEL_PRESET=lm-studio python -m edm_auditor.rag search "условия оплаты"
```

Ручной API smoke-тест после запуска сервера:

```bash
curl -X POST http://127.0.0.1:8000/api/documents/upload \
  -F "file=@contract.txt"
curl -X POST http://127.0.0.1:8000/api/documents/<id>/audit
curl http://127.0.0.1:8000/api/documents/<id>/report
```
