# План разработки: `feature/audit-configuration-stage-2`

> **Статус:** реализовано. Второй этап текущей ветки
> `feature/audit-configuration`. Правила типа `semantic` через API пока не
> выполняются, поэтому этап подбора RAG-контекста работает только как рекомендация.
>
> Этап посвящён определению применимости правил к пользовательскому документу.
> Первый этап обеспечивает корректное извлечение и публикацию правил из НПА,
> второй этап должен определить, какие из опубликованных правил применять к
> конкретному документу.

## 1. Назначение этапа

После первого этапа система умеет извлекать, валидировать, сохранять и
индексировать правила из нескольких НПА. Однако при запуске аудита сейчас
выбираются все активные правила, если они не ограничены совпадающим
`document_type`. Автоматически сгенерированные правила часто имеют
`document_type = NULL`, поэтому фактически считаются универсальными.

Это приводит к ложным нарушениям: документ о командировке может проверяться
одновременно правилами НПА о командировках, дистанционной работе и оплате труда.

Результатом этапа должен стать воспроизводимый pipeline:

```text
upload document
  -> classify document
  -> resolve applicable legal acts and rules
  -> preview or confirm selection
  -> run deterministic and semantic audit
  -> persist selection configuration
  -> publish explainable report
```

## 2. Цели и результат

После завершения этапа система должна:

1. Определять тип или типы пользовательского документа до запуска аудита.
2. Связывать правило с областью документов, к которым оно применимо.
3. Выбирать только релевантные правила, а не все активные правила базы.
4. Сохранять возможность применять действительно универсальные правила.
5. Позволять пользователю явно выбрать НПА или набор правил перед аудитом.
6. Разделять автоматический отбор, ручной выбор и принудительный режим.
7. Показывать в отчёте применённые НПА, правила и причины выбора.
8. Показывать причины исключения нерелевантных правил.
9. Не использовать низкокачественный семантический поиск как единственное
   основание для включения правила.
10. Сохранить обратную совместимость ручных правил и существующих отчётов.

## 3. Границы этапа

### Входит в этап

- каталог типов пользовательских документов (с поддержкой динамического добавления и безопасного удаления/деактивации);
- модель области применимости правила и НПА;
- автоматическая классификация документа;
- фильтрация правил до вызова `AuditEngine`;
- ручной выбор НПА или набора правил через API и web UI;
- режимы `automatic`, `manual`, `combined` и явно подтверждённый `all`;
- предварительный просмотр применяемых правил;
- сохранение конфигурации аудита в отчёте;
- безопасное использование RAG для рекомендации релевантного контекста;
- unit-, integration- и regression-тесты на нескольких НПА;
- обновление API-документации и руководства по отладке.

### Не входит в этап

- юридическое утверждение применимости правила;
- автоматическое изменение юридического смысла или severity правила;
- OCR и поддержка новых форматов документов;
- обучение собственной классификационной модели;
- полноценная авторизация, RBAC и разделение наборов по пользователям;
- асинхронная очередь аудитов;
- генерация исправленной версии документа;
- замена детерминированных валидаторов на LLM;
- удаление старых отчётов или изменение их исторического содержания.

Если тип документа не определён с достаточной уверенностью, система не должна
молча применять все правила. Она должна вернуть состояние `needs_configuration`,
показать предложенные варианты и позволить ручной выбор.

## 3.1. Политика выбора правил

Для обычного запуска применяется ограниченный набор правил. Режим `all` не
является скрытым fallback и доступен только при явном выборе пользователя.

Приоритеты выбора:

1. явное исключение пользователя;
2. явное включение пользователя;
3. выбранные пользователем НПА;
4. любой подтверждённый тип документа;
5. универсальность правила;
6. автоматическая рекомендация классификатора и RAG.

Автоматическая рекомендация не должна переопределять явный выбор пользователя.
Неизвестная область применимости не должна автоматически превращаться в
универсальную.

## 4. Текущие проблемы и целевые инварианты

### 4.1. Область действия правила

Правило должно иметь одну из областей:

```text
universal
typed
manual_only
unknown
```

Правило области `typed` применяется только при совпадении с типом документа.
Правило области `manual_only` применяется только после явного включения.
`unknown` требует ручного решения и не включается автоматически. `unknown` — это
состояние неопределённой применимости, а не обычный тип документа из каталога.

### 4.2. Классификация документа

Классификация должна возвращать:

```text
confirmed_document_types
confidence
classification_status
candidate_types
source
```

Поддерживаются состояния:

- `classified` — тип определён;
- `needs_review` — есть кандидаты, но уверенность недостаточна;
- `unknown` — тип определить не удалось.

Ручное переопределение должно иметь приоритет, но исходная автоматическая
классификация сохраняется для диагностики. Неподтверждённый `candidate_types`
не может сам по себе включить typed-правило.

Один документ может иметь несколько подтверждённых типов. Если документ имеет
типы `business_trip_order` и `travel_expense_report`, typed-правило считается
применимым при совпадении хотя бы одного типа (логика OR). Логика AND не
используется по умолчанию.

### 4.3. Выбор НПА и правил

До запуска `AuditEngine` должен выполняться отдельный resolver. Только
выбранные им правила передаются в движок аудита.

Минимальные инварианты resolver-а:

- неактивные правила никогда не выбираются;
- правило конкретного типа выбирается только при совпадении типа;
- правило конкретного НПА выбирается только если НПА входит в scope;
- универсальные правила выбираются отдельно и явно отображаются;
- явное исключение сильнее автоматической рекомендации;
- одинаковое правило не передаётся в `AuditEngine` дважды;
- отсутствие подходящих правил даёт диагностируемый результат, а не успешный
  пустой аудит без объяснения.

### 4.4. RAG и embeddings

RAG используется для поиска релевантного контекста и ранжирования кандидатов,
но не является единственным основанием для включения правила. Для каждого
кандидата должны быть доступны `legal_act_id`, `rule_id`, score и threshold.

Если RAG недоступен, детерминированный режим должен продолжать работать для
обычных правил. Низкий score не должен автоматически создавать finding.

## 5. Предлагаемая структура модулей

```text
backend/
  src/edm_auditor/
    classification/
      models.py          # document types and classification result
      classifier.py      # deterministic baseline and overrides
    applicability/
      models.py          # selection config and resolver result
      resolver.py        # applicable rule selection
      persistence.py     # audit selection snapshot
    audit_engine/
      persistence.py     # pass resolved rules and save report metadata
    api/
      app.py             # classification, preview and audit endpoints
      schemas.py         # public request/response contracts
      web.py             # selection controls and report details
  tests/
    classification/
    applicability/
    api/
```

Допускается разместить часть логики в существующих модулях, если классификация
и выбор правил останутся отделены от SQLAlchemy, FastAPI и конкретного
embedding/LLM-провайдера.

## 6. Контракты и модель данных

### 6.1. Тип документа

Начальный каталог должен включать:

```text
employment_contract
business_trip_order
remote_work_agreement
payroll_order
vacation_order
```

Для каждого типа хранятся технический код, пользовательское название и
описание. `unknown` не является записью каталога и используется только как
состояние классификации или применимости. Каталог хранится в базе данных,
поддерживает динамическое добавление новых типов документов, а также безопасное
удаление или деактивацию (soft delete) с проверкой зависимостей (активные
правила и загруженные документы). Один документ может иметь несколько
кандидатных и подтверждённых типов с confidence.

### 6.2. `Document`

Добавить или нормализовать поля:

- `classified_type`;
- `classification_confidence`;
- `classification_status`;
- `classification_candidates`;
- `classification_source`.

Полный текст документа не должен попадать в диагностические ответы и логи.

### 6.3. `AuditRule`

Добавить структурированную область применимости:

- `applicability_scope`;
- связь many-to-many с типами документов через таблицу
  `rule_document_types(rule_id, document_type_code)`;
- `applicability_confidence`;
- `applicability_source`.

Одно правило может быть связано с несколькими типами документов, а один тип —
с несколькими правилами. Для typed-правила наличие хотя бы одного совпавшего
подтверждённого типа достаточно для выбора.

Существующие `legal_act_id` и provenance сохраняются независимо от области
применимости. Старое одиночное поле `document_type`, если оно уже заполнено,
должно быть перенесено в `rule_document_types` миграцией. После миграции API и
доменный контракт не должны зависеть от одиночного значения.

### 6.4. Конфигурация аудита

Сохранять вместе с отчётом снимок:

```json
{
  "selection_mode": "automatic",
  "selected_legal_act_ids": [],
  "included_rule_ids": [],
  "excluded_rule_ids": [],
  "confirmed_document_types": [],
  "candidate_document_types": [],
  "classification_confidence": 0.0,
  "selection_reasons": []
}
```

Снимок нужен для объяснения старого отчёта после изменения правил, НПА или
классификатора.

## 8. Требования к целостности и ошибкам

- Нельзя передавать в `AuditEngine` все активные правила без явного режима `all`.
- Режим `all` не может использоваться как автоматический fallback и должен
  отображаться как широкий административный/диагностический запуск.
- Нельзя считать неизвестную применимость универсальной.
- `unknown` не должен использоваться как обычный тип документа из каталога.
- Явное исключение пользователя не может быть отменено автоматической
  классификацией или RAG.
- Неподтверждённый candidate type не может самостоятельно включить typed-правило.
- Для правила, связанного с несколькими типами, достаточно одного совпавшего
  подтверждённого типа; отсутствие одного из остальных типов не исключает
  правило.
- Низкая уверенность классификатора должна быть видна пользователю.
- RAG не должен быть единственным источником решения о применимости.
- Отсутствие релевантных правил должно иметь явную диагностику.
- Конфигурация выбора должна соответствовать фактически созданному отчёту.
- Исторический отчёт не должен изменяться после изменения правил или
  классификатора.
- Полные пользовательские тексты, prompt, raw response и секреты нельзя
  записывать в логи, ошибки или API-ответы.
- Детерминированные проверки не должны исчезать из-за ошибки классификатора или
  RAG.

## 9. Критерии готовности

Этап считается завершённым, если:

- для документа сохраняется классификация или состояние
  `needs_configuration`;
- автоматически сгенерированные правила имеют определённую или диагностируемо
  неизвестную область применимости;
- одно правило может быть связано с несколькими типами документов и выбирается
  при совпадении любого подтверждённого типа;
- аудит выполняется только по выбранным или релевантным правилам;
- пользователь может увидеть набор правил до запуска аудита;
- отчёт содержит использованные НПА, типы документа и конфигурацию выбора;
- ручные включения и исключения работают предсказуемо;
- режим `all` доступен только явно и отображается как потенциально широкий;
- RAG не используется как неконтролируемый fallback;
- integration-тест с тремя НПА подтверждает отсутствие нерелевантных findings;
- существующие отчёты и детерминированные валидаторы не ломаются;
- документация описывает ограничения автоматической классификации и
  необходимость ручной юридической проверки.

Минимальный integration fixture должен включать:

```text
ACT-REMOTE     -> remote_work_agreement
ACT-TRIP       -> business_trip_order
ACT-PAYMENTS   -> payroll_order
```

Для документов о дистанционной работе и командировке ожидается проверка только
релевантных правил, а не суммарного набора всех трёх НПА.

## 11. Рекомендуемая последовательность коммитов

```text
docs(config): define legal-act applicability stage
feat(classification): add document type catalog and deterministic classifier
feat(rules): add rule applicability scope and document type mapping
feat(audit): resolve applicable rules before running audit
feat(api): add classification and audit selection preview endpoints
feat(ui): add rule selection and audit preview controls
feat(reports): persist audit selection configuration and provenance
test(audit): cover multi-legal-act applicability scenarios
docs(config): document stage two audit configuration workflow
```

Все изменения выполняются в ветке `feature/audit-configuration`. Этап должен
использовать результаты первого этапа — provenance, `legal_act_id`, статусы НПА
и RAG-контекст — но не смешивать выбор применимых правил с их извлечением или
юридическим утверждением.
